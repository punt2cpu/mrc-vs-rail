# mrc-vs-rail

Small containerlab lab to see how a classic rail-optimized AI back-end (eBGP, BFD, per-flow ECMP) behaves next to the MRC approach (multi-plane, static SRv6 uSID, host picks the path for every packet, no routing protocol on the switches).

MRC side follows the description on [srv6.md](https://srv6.md/ai/mrc/) and the [MRC paper](https://cdn.openai.com/pdf/resilient-ai-supercomputer-networking-using-mrc-and-srv6.pdf), scaled down to 2 hosts.

## Topologies

Both labs have 2 hosts with 8 links each and 32 fabric links.

![topologies](img/topology.svg)

Every node, with the config of one host, one leaf or T0 and one spine or T1:

![rail full topology and configs](img/rail-full.png)
![mrc full topology and configs](img/mrc-full.png)

**rail** - 18 switches, FRR

```
                 s1                    s2               every leaf has one link to each spine
   leaf-a0 ... leaf-a7          leaf-b0 ... leaf-b7     one leaf per rail per pod
   srv1 eth1 ... eth8           srv2 eth1 ... eth8      ethN -> leaf of rail N-1
```

A host here is 8 GPUs with one NIC each. GPU n on srv1 talks to GPU n on srv2 over rail n only (4 QPs per GPU, 32 total). Leaves hash each QP onto s1 or s2. eBGP unnumbered with BFD 50 ms x3.

**mrc** - 32 switches, FRR with staticd only

```
plane 0:      t1c-p0      t1d-p0
          t0a-p0      t0b-p0
          srv1 eth1   srv2 eth1
...
plane 7:  same, srv1 eth8 / srv2 eth8
```

A host here is one 800G NIC broken out into 8 ports, one port per plane. Each plane is its own small 2-tier Clos. The 32 QPs send every packet on the next live path out of 16 (8 planes x 2 T1). The path is written into the destination address:

```
fcbb:bb00 : a00 : d00 : b00 : e002 ::
block       src T0 T1    dst T0 port on dst T0
```

Every switch has one static uN SID for itself (shift 16 bits, forward on the rest) and static /48 routes to its neighbours. That's all. The host does encap and decap (IPv6 in IPv6), probes every path every 50 ms and drops a path after 3 lost probes in a row.

Same number of host and fabric links, but mrc needs more and smaller switches. In rail one tier-1 switch carries half the traffic, in mrc one of 16.

## Run

Needs Linux with kernel and iproute2 6.1 or newer for the mrc lab (`next-csid`). Ubuntu 24.04 works.

```bash
git clone https://github.com/punt2cpu/mrc-vs-rail.git && cd mrc-vs-rail
./lab.sh all
```

`all` installs docker and containerlab if they're missing, builds the node image (pulls FRR 10.7.1), loads the kernel modules the tests need, checks that the kernel can do SRv6 uSID, then brings up each lab, runs the three tests, tears it down and prints the results. About 3 minutes per lab plus the first image build.

If the kernel is too old for uSID (before 6.1), on Ubuntu `all` installs the HWE kernel and asks for one reboot. On other distros it runs the rail lab only.

Single steps:

```bash
./lab.sh setup                       # install what's missing, build image, check kernel
./lab.sh up rail                     # or mrc
./lab.sh test rail link              # spray, link or switch
./lab.sh down rail
./lab.sh results                     # all runs, then median (min-max) per lab and test
./lab.sh summary                     # only the median part
```

`./lab.sh all 10` runs everything 10 times. Each round redeploys both labs, so rail hashes the QPs onto the spines differently every time.

`labs/` is generated by `gen.py` (2 hosts, 8 links, 32 QPs, 1000 pps per QP, 50 ms detection - all at the top of the file). Change it and run `python3 gen.py` again.

## Tests

Traffic: 32 QPs from srv1 to srv2, 1000 packets per second each, so one lost packet is one millisecond of one QP.

| test | what happens | rail | mrc |
|---|---|---|---|
| spray | 10 s of traffic, no fault, packets per pod A uplink | uneven, per-flow hashing | even |
| link | one T0 to T1 link drops everything for 10 s, carrier stays up (silent) | the QPs hashed onto it lose everything until BFD + BGP reroute | all QPs lose a few packets until the path is dropped |
| switch | one T1 drops everything it forwards for 10 s, BGP and BFD stay up (silent) | about half the QPs dead until the fault is removed | one of 16 paths, dropped like in link |
| flap | the same link loses carrier for 2 s every 10 s, four times | carrier loss is seen at once, BGP session resets every time | path dropped and taken back every time |
| t0down | one T0 goes down completely, all its links lose carrier, for 10 s | the GPUs on that rail have no other path, dead until restore | 2 of 16 paths gone, QPs keep the other 14 |

The rail and mrc columns are what's expected. The point of running it is to see if that holds.

Each run ends up in `results/<date>-<lab>-<test>/`: sender and receiver data, `events.log` (START, INJECT, RESTORE, END), `timeline.txt` and `summary.json`.

## Reading the results

`./lab.sh results` prints every run, then median (min-max) per lab and test.

| column | meaning |
|---|---|
| QPs w/ loss | QPs that lost at least one packet, out of 32 |
| lost | packets lost over all QPs (64-byte UDP, 1000 per second per QP) |
| worst QP | packets lost by the QP that lost most. For a QP cut off completely, this is also its outage in ms |
| loss window | ms from the first to the last lost packet over all QPs. `+` = still losing when the fault was removed |
| uplinks | spray only: busiest pod A uplink / quietest one, 1.0x = perfectly even |

Spray has no fault, so `0 / 0 / 0 / -` is the expected clean result. That run is the control: if it ever shows loss, the lab itself is broken and the failure tests can't be trusted.

## Watching a test

In a second terminal while a test runs:

```bash
sudo ./lab.sh watch rail
```

One line every 100 ms, one character per QP: `#` everything arrived, `-` some packets missing, `.` nothing arrived. The same lines are saved as `timeline.txt` in the run folder. A link failure should look roughly like this in the two labs:

```
rail                                        mrc
21:46:25.3  ################################    21:47:41.2  ################################
21:46:25.4  ##.#####.#######################    21:47:41.3  --------------------------------
21:46:25.5  ##.#####.#######################    21:47:41.4  --------------------------------
21:46:25.6  ################################    21:47:41.5  ################################
```

## Checking the numbers

- Arithmetic: a rail QP cut off for 190 ms at 1000 pps loses ~190 packets. An mrc QP sends 1 of every 16 packets on the broken path, so in 190 ms it loses 1000 / 16 x 0.19 = ~12. Both match what the tests report.
- Independent count: the link test reads netem's own drop counter on the broken link (`netem-a.txt`, `netem-b.txt`). It counts the test traffic plus BFD or probe packets in both directions, so it is a little higher than `lost`, never lower.
- Packets: `tcpdump` on any node shows the real traffic, e.g. the uSIDs shifting hop by hop in the mrc lab:
  `sudo docker exec clab-mrc-t1c-p0 tcpdump -lni eth1 ip6 proto 41`

## What it doesn't show

- Speeds and real latency. Software forwarding on veth links, millisecond resolution at best
- PFC, DCQCN, congestion, incast, packet trimming
- MRC reacts to loss within tens of microseconds in the NIC. Here it's a probe every 50 ms, same budget as BFD
- RDMA. Traffic is UDP with sequence numbers per QP
